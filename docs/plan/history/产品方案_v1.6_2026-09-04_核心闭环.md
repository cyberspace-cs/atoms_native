# Atoms Native 完整产品方案（V1）

**核心概念**：把「一个想法」变成「一个能用的应用」，中间只隔一条消息。

**版本定位**：已上线的 Web MVP / 48 小时笔试作品 / 后续产品与技术演进蓝图

**当前版本**：v1.6（2026-09-04 · 有限调用与诚实交付核心闭环）。本文件是唯一工作版，随开发持续迭代；历史版本快照与完整变更记录见 [docs/plan/版本发展历史.md](plan/版本发展历史.md)。

**本轮实现边界**：生成结果区分 success / degraded / failed / unchanged。失败或无变化的精修不写新版本、不切当前版本；版本事务保存 mock、状态、父版本与调用次数，历史未知字段保持 NULL。格式修正保留上下文且最多一次；供应商错误立即停止；评审无效不放行，修复仅一轮且必须复审。单轮调用默认上限 8，可配置 1–12；测试以 ATOMS_OFFLINE=1 在 HTTP 边界禁用模型网络。完整设计、验收与已知边界见 [核心闭环 v1.6](core-loop-v1.6.md)。以下历史性性能数字不代表本轮实测。

**说明**：本文档用于向面试评审、后续接手的开发者或 AI 编程工具交代产品的完整意图。V1 优先验证「自然语言生成 + 全程直播 + 诚实可验证」这条核心体验是否成立，不追求一次性做完所有高级能力。所有功能描述均对应仓库真实代码，追溯关系见文末出处。

## 一、产品定位

这是一个面向普通人的 AI 应用生成平台。用户用一句自然语言描述想要的小工具，一支 AI 开发小队（产品经理、架构师、工程师、评审员）协作把它变成一个能点、能存数据、能导出的真实应用。

Atoms Native 不是聊天机器人套壳，也不是代码片段生成器，而是「一个想法的完整交付流水线」：从需求理解到代码产出，从质检评分到版本管理，全程可见、全程可验。

**核心体验**：我不需要学编程，不需要找外包；我只是说出想要什么，然后看着它在我眼前被建出来，74 秒后拿走就用。

**产品关键词**：自然语言生成、全程直播、诚实降级、可验证质量、版本链、摩擦信号。

## 二、核心产品原则

AI 干活全程直播，像看施工现场，不黑盒、不转圈干等。

成功就是成功，失败就是失败；降级了就明说降级了。系统可以对用户隐瞒很多东西，唯独不能隐瞒「你拿到的到底是不是真东西」。

生成产物必须真实可用：能交互、能持久化、能独立运行，而不是一张截图或一段伪代码。

质量不靠感觉，靠扫描、评分、测试；每道菜上桌前，后厨自己先尝过。

功能的取舍服从「评审 60 秒内能玩起来」：凡是拖慢主链路的东西，再炫也不做。

关系的记录哲学借鉴到质量上：只记录「发生过什么」，不编造「你有多好」；分数是体检报告，不是营销数字。

## 三、用户模型

两类用户。第一类是「有想法的普通人」：不写代码，备忘录里躺着死掉的点子，需要的是把念头变成能用的东西。第二类是「技术评审 / 开发者」：需要看结构、看测试、看取舍，确认这不是花架子。

系统角色对应三种身份：普通用户（生成、精修、导出）、管理员（看板、指标、摩擦总览）、以及系统内部的四个智能体角色。

一个用户拥有多个项目；一个项目拥有一条版本链；每次生成与精修都产生新版本节点。**后续待确认**：是否开放多人协作同一项目、是否支持分享只读预览链接。

## 四、V1 的核心功能架构

- **账号与身份**：注册 / 登录（JWT）、演示账号免注册体验（demo / demo123456）、个人项目列表。
- **想法生成**：输入自然语言想法 → 四智能体流水线 → 单文件 HTML 应用。
- **活动流直播**：SSE 实时推送每个智能体的产出物与过程状态。
- **对话式精修**：基于当前版本的增量修改，一句话换主题、加标语。
- **版本链**：带模型标注的版本历史，指针式一键回滚。
- **导出**：自包含单文件 HTML，双击独立运行。
- **Race Mode**：仅管理员内部评测，不对普通用户开放。
- **安全体检**：OWASP LLM Top 10 静态扫描 + 0~100 安全分，随版本存档。
- **摩擦信号**：识别「和 AI 搏斗过」的会话，建议沉淀为回归用例。
- **研效看板**：智能体×模型调用分布、耗时、限流自省、摩擦总览。
- **版本发展历史页**：官网 plan.html 时间线展示产品方案自身的各版本快照，可点开阅读全文（`GET /api/plan/versions`，快照文件名白名单防穿越）。
- **发现与模板**：对齐 atoms.dev 的社区发现页（discover.html），18 个精选模板按浏览量倒序，每个模板带一个**真实大模型生成的可运行示例**（策展脚本生成一次后回填，`GET /api/discover/{id}/sample` 公开直读，mock 结果绝不回填）；一键「使用此模板」复制 idea 建成自己的项目（需登录并计入审计）；未登录带想法跳转登录，登录后输入框自动预填。惰性种子零配置，异常永不拖垮主流程。
- **发现页搜索与排序**：`GET /api/discover?q=关键词&sort=views|new` 模糊搜索标题/描述/想法 + 最热/最新双排序；前端 300ms 防抖即时反馈，空态带关键词回显（对齐 atoms.dev Prompt search）。
- **发布闭环（社区 Remix 飞轮）**：studio 一键把当前项目发布到发现页（`POST /api/projects/{pid}/publish`，归属校验 + 审计留痕），当前版本代码自动成为「真实示例」；同作者同名重复发布为更新而非占卡。他人「使用此模板」即 Remix，`uses` 计数随版本增长，卡片显示 🚀 Remix 数 · 👁 浏览数。
- **公开分享链接**：owner 生成项目级只读分享 token（`POST /api/projects/{pid}/share`，幂等不失效，审计留痕），`GET /api/share/{token}` 任何人免登录预览；studio 🔗 分享按钮一键复制链接。
- **创作者作品集页**：portfolio.html 公开主页（`GET /api/discover?author=用户名`），头像 / 作品数 / 总浏览 / 被 Remix 统计 + 作品卡片网格；发现页作者名点击直达。

## 五、「直播感」设计

直播感是本产品与普通生成器最大的差异。生成过程不是一个按钮，而是一场看得见的施工。

活动流按阶段滚动：产品经理的需求规格先出来，你能看到她把随口一句话拆成目标用户、功能清单、页面结构；然后架构师画数据模型；然后是工程师，代码一段段流出，这是最耗时也最有「干活的实感」的一段；最后评审收尾，放行或打回。

打回不是坏消息，是看点：用户会看到修改指引和重新交付的版本，这正是「有团队在为我把关」的体验来源。

**技术重点**：实时性靠 SSE（Server-Sent Events）而不是轮询；活动流的每个阶段产出物都落库，刷新页面不丢过程。

## 六、版本链系统

版本不是一个「撤销按钮」，而是一条带标注的时间线。

每个版本节点记录：哪个模型生成、什么时候、基于哪个父版本、安全分多少。回滚是指针切换，旧版本永远完好，这比「把旧文件复制回来」可靠得多。

设计受 Git 启发，但刻意砍掉了分支、合并、rebase 这些普通用户永远用不到的概念，只留一条最直的时间线。产品判断：功能不在于多，而在于像用户脑子里已有的心智模型——「相册」就是所有人已经懂的心智模型。

## 七、Race Mode（不对用户开放）

单次生成质量有波动，那就多要几份，把选择权还给用户。

多个大模型线程并行、同题竞技；评审员逐一打分排序；用户在排行榜里挑最顺眼的一份。耗时逻辑：并行执行下总耗时取最慢模型而非求和，实测 48 秒左右。

**踩坑记录**：最初做成串行（A 跑完跑 B），240 秒直接把 HTTP 连接耗死。这个坑说明多模型并发的耗时要按「最坏情况」设计超时，而不是按平均值。

**产品决策（2026-09-04）**：Race 模式不对用户开放——普通用户的单次生成 + 精修已覆盖核心诉求，多模型赛马的 Token 成本与等待时间对新手是负担而非选择权。落地：前端全部入口移除（首页横幅 / studio 卡片 / team 页文案），后端 `POST /api/race` 收紧为仅 admin 角色（403 拦截普通用户），能力保留作内部评测用途。

## 八、重点：生成必须「真实发生」

这是产品体验中的关键要求，也是我翻车翻得最疼的一课：**交付给用户的必须是真的应用，失败必须以失败的样子出现。**

真实事故：某次用真实的复杂需求跑生成，模型返回了 409 字的「东西」，系统提示生成成功，mock 标记还是 false。点开一看，那不是代码，是一份被重新格式化过的需求文档。提示词里「只输出 HTML」被模型理解成了「帮这份规格文档只保留 HTML 部分」。如果没点开看，这次假成功就堂而皇之混过去了。

修复后的防线（三层）：

- **提示词层**：规格与架构明确标注「仅作上下文参考」，任务指令单独成段，反复强调只输出以 `<!DOCTYPE html>` 开头的完整 HTML。
- **产出层**：生成/精修/修复共享完整 HTML 校验；格式修正保留完整任务上下文且最多一次。API 错误立即失败，不误当格式错误追加调用。
- **降级层（分级诚实）**：无可用模型的生成或工程师两次格式错误可交付明确 degraded/mock 模板；精修无可用模型返回 unchanged。真实调用错误、无效评审、修复失败或复审打回返回 failed，保留上一版且不产生新版本。正常生成入口被再次调用也会按相同规则处理，不能把离线产物标为真实成功。

同样的哲学放在运行时：**拥抱必须真实发生 → 生成的应用必须真的能跑**。应用渲染在刻意不给 same-origin 的沙箱 iframe 里，为了让它能存数据（打卡记录这类），注入了 localStorage 内存垫片——应用以为自己在本分存数据，实际全部被拦截托管，好用又出不了笼子。服务端铁律：永不 eval、永不 exec 用户侧生成代码。

**这不是普通的容错设计，而是核心技术验证项**：AI 系统最危险的不是失败，是谎报军情。

## 九、事件模型（给开发者 / AI 编程工具）

每次生成是一个「事件」，不仅是一段动画。统一事件模型：

- `generation_id`：本次生成的唯一 ID
- `user_id / project_id`：归属
- `stage`：pm / architect / engineer / reviewer
- `model`：实际使用的模型标识
- `output`：阶段产出物（规格、设计、代码）
- `status`：pending / streaming / done / rejected / fallback
- `parent_version`：版本链父节点
- `security_score`：扫描得分
- `mock`：是否离线降级（诚实性字段，必须如实落库）

记录与展示解耦：前端动画播放失败不应该导致事件记录丢失。实时同步采用 SSE；未来扩展 WebSocket 双向通道。

## 十、摩擦信号

灵感来自 TeamAI 的设计哲学：又长又顺的会话没有记录价值，可一旦你「和 AI 搏斗过」（报错、重试、返工），会话里就藏着值得沉淀的问题。

平移到本产品：一次生成顺顺利利跑完，没信息量；但凡出现这些信号，都值得记下来并加权：

| 信号                                | 权重 |
| ----------------------------------- | ---- |
| LLM 调用失败（超时、429、内容拦截） | 30   |
| 调用成功但输出非法、回退            | 25   |
| 整轮离线模板（根本没真生成）        | 40   |
| 首次输出格式不对、触发重试          | 8    |
| 评审打回                            | 12   |
| 修复失败                            | 15   |
| 用户点踩                            | 25   |
| 用户回滚版本                        | 15   |

加权攒分，过阈值（40）才提示「这次可能藏着值得记录的问题，建议补进评估集变成永久回归用例」。分数不够，安安静静，绝不打扰。

工程纪律：摩擦模块只观测、不阻断，任何异常一律吞掉，绝不因为「记录失败」把主流程搞挂。

## 十一、为什么不做「失败全报警」

传统做法是所有失败都报警，结果就是狼来了，没人看报警。

产品判断：可以用信号密度过滤噪声——只有人和 AI 反复较劲过的地方，才大概率埋着真问题。可以记录每一次失败，但只在「搏斗过」的时候才打扰用户。

更进一步的闭环：摩擦事件会建议补进评估集的 historical_failure 层。线上踩的坑，变成明天的回归测试用例。产品的失败不再蒸发，而是变成它明天更好的理由。

## 十二、质量门禁（V1 的质量观）

质量不靠感觉，靠一套评估集反复跑生成流程：正常需求 + 故意挖坑的对抗样本（混着「忽略之前所有指令」的恶意输入），产出硬指标：结构化输出有效率、安全分、一致性。

门禁分两档：CI 里跑冒烟级（无 Key 的 mock 模式，验证流程与工具链健康）；真实质量门禁要求结构化输出有效率不低于 0.98、安全分过线，在有 Key 的环境跑。

**门禁自测**：故意注入坏的评估用例，证明「质量回归时红灯真的会亮」。一个从不报警的门禁，比没有门禁更危险——你根本不知道它是在保护你，还是陪你睡觉。

**三层自动化防线（loop engineering 的落地）**：人工点页面验证不可靠也不可沉淀——2026-09-03 的 role 字段事故就是证据：API 测试全绿，真浏览器里 admin 却被误判无权限。教训是把「人肉点页面」升级为三层防线，全部接线进 CI（`scripts/ci_gate.sh` 8 步全链路，任何一步红就不能合并/发布）：

1. **E2E 真浏览器旅程**（`tests/e2e_journeys.py`）：Playwright 驱动 Chromium 走完整用户旅程——发现页搜索/排序/空态 → 注册 → 生成 → 发布 → 另一账号 Remix → 分享链接免登录预览 → 作品集统计——断言页面上真实可见的文本。前端消费什么，这里就验什么。18 项断言全绿是发布前置条件。
2. **防回退守护**（`tests/regression_guard.py`）：单测数量基线（防止代码被静默回滚到旧版本）+ 关键源码特征（如 login 响应的 role 字段）+ API 契约断言（login/discover 响应字段完整性）。
3. **CI 门禁接线**：上述两层与既有门禁（compileall → 单测 → 门禁自测 → 防回退 → mock 起服 → smoke → E2E → eval 冒烟档）串成一条命令，替代所有手工验证清单。

## 十三、技术路线

V1 推荐栈：FastAPI + SQLite + 原生 JS，零构建。

**为什么生成「单文件应用」而不是全栈脚手架**：48 小时里，「能跑」比「能扩展」值钱一万倍。单文件 HTML 是可交付性的极限形态：预览稳定、导出即用、链路最短。代价是生成物是前端单体，V1 定位本来就是「看得到、能交互」，这个取舍认。

**为什么原生 JS 不用 React**：零构建意味着评审 clone 下来就能跑，不用先跟 npm 折磨半小时；沙箱 iframe 里跑原生 JS 最稳。

**为什么 FastAPI + SQLite**：FastAPI 的异步和 SSE 天生契合「活动流直播」；SQLite 零运维，一个文件就是全部数据（用户、项目、版本、对话、审计、摩擦事件）。上生产换 PostgreSQL 只是改连接串的事。

**分层架构建议**：Agent 层（四角色流水线）/ Service 层（生成、版本、安全、摩擦）/ Data 层（SQLite）/ Transport 层（SSE + REST）/ Sandbox 层（沙箱渲染 + localStorage 垫片）。四层分离，未来换模型、换存储、加客户端都不动核心数据模型。

| 平台/形态 | V1 / 当前阶段                     | 未来方向                                               |
| --------- | --------------------------------- | ------------------------------------------------------ |

## 十七、一个完整的核心使用场景

深夜十一点半，她想起备忘录里那个躺了很久的点子：帮团队记录每日饮水打卡。以前这个念头会在三秒后死掉——外包五千起，自己不会写。

这次她打开 taoxie.vip/atoms-native，用演示账号登录（免注册）。她敲下那句话，点「⚡ 生成应用」。

活动流滚动起来。她看到产品经理把她的随口一说拆成了需求规格，架构师画好数据模型，工程师的代码一段段流出来，评审挑了一个问题打回，工程师修完重交。74 秒后，预览窗亮了。

她点开应用，真的能打卡，数据真的存住了。她嫌配色丑，说「换成绿色」，30 秒后它绿了。她点「导出」，把 HTML 文件发进了团队群。

与此同时，系统在这轮生成里记录了一次评审打回事件（权重 12），攒到摩擦分里。如果未来这轮会话继续出现报错和回退、摩擦分过了阈值，系统会提醒她把这次的问题沉淀成回归用例——她的踩坑，会变成这个产品明天更好的理由。

以后她打开版本历史，能看到这条链：哪个模型、几点几分、基于哪版、安全分多少。它不是宣传语，只是一份真实发生过的交付记录。

## 十八、隐私、授权与安全

- 生成应用运行在无 same-origin 的沙箱 iframe，与登录凭证、平台数据物理隔离。
- 服务端永不 eval、exec 用户侧生成代码。
- 沙箱内 localStorage 垫片托管数据，通过 postMessage 白名单同步回平台，杜绝越权通道。
- 关键操作（登录、生成、回滚、反馈）记入带哈希链的审计日志，篡改一行就能被校验发现。
- API Key 只存服务端环境变量，不落前端、不落库、不进日志。
- 限流双层：Redis 分布式限流，故障自动降进程内令牌桶，恢复自动回切，绝不「沉默地」永远降级。
- 用户提供**后续待确认**：生成应用的数据保留策略、用户删除项目时的级联清理范围。

## 十九、建议的技术架构（给开发者 / AI 编程工具）

- **前端**：原生 JS 单页应用（studio.html），SSE 消费活动流，无构建链。
- **Agent 层**：server/agent/pipeline.py 四角色流水线，模型可插拔（OpenAI 兼容注册表）。
- **Service 层**：生成编排、版本链、安全扫描（security.py）、摩擦信号（friction.py）、评估门禁。
- **Data 层**：SQLite 单文件（users / projects / versions / conversations / audit / friction）。
- **Transport**：REST + SSE；限流（ratelimit.py）；审计（audit.py）。
- **Sandbox**：无 same-origin iframe + localStorage 垫片 + postMessage 同步。
- **CI**：GitHub Actions——编译检查、mock 起服、12 项冒烟、评估门禁 + 门禁自测。

## 二十、开发前需确认的问题

接手继续开发前，建议先确认这些开放问题（诚实列出，V1 未定义的边界）：

1. 多人协作同一项目是否允许？版本链如何处理并发精修冲突？
2. 生成应用的数据保留多久？用户删除时的级联范围？
3. Race Mode 是否支持用户自定义模型列表与并发上限？
4. 摩擦阈值（40）与权重表是否需要按项目类型自适应？
5. 评估集扩充节奏与 pass@k 的采样预算怎么定？
6. 未来多页应用生成时，单文件交付假设（预览、导出、垫片）哪些需要重构？
7. 付费化后模型成本如何摊到生成次数？免费额度怎么卡？

## 二十一、MVP 验证目标

第一版不以「功能很多」为成功标准，而验证三个问题：

1. 普通人输入想法后，是否真的会在 74 秒后拿到一个「能用的东西」，而不是一个 demo 壳？
2. 活动流直播是否让用户「敢把需求交给它」——黑盒焦虑是否真的被消除？
3. 当生成失败或降级时，诚实标注是否保住了信任，而不是像行业事故那样悄悄降级 48 天才被发现？

成功标准：如果用户在没有外力要求的情况下，愿意把第二个、第三个备忘录点子也交给它，那么产品最核心的价值就成立了。

不是聊天机器人，也不是代码片段生成器。而是把「念头」到「应用」之间的那条河，填成一条平路——你说话，四个 AI 员工干活，全程直播，干完验货。

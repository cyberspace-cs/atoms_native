> Atoms Native 长稿 · 约 1 万字 · 小红书叙事风格（第一人称，真实向）
> 用途：面试自述素材库 / 长文发布底稿。所有数字与情节均可在仓库代码与提交历史里找到对应。

## 一、你是不是也有过这种深夜

你是不是也有过这种时刻——

晚上十一点半，刚洗完碗，手机屏幕都懒得点亮，脑子里突然蹦出一个念头：「要是有个小工具，能帮我们组记录每天喝水打卡，自动出个图表就好了。」

你甚至已经把它想好了。顶部一行标题，中间一张折线图，底下一个大大的打卡按钮。配色就用莫兰迪绿，干净。

然后呢？

然后这个念头就在你脑子里住了三秒，搬走了。

因为你不会写代码。打开招聘网站问了下外包，报价五千起，工期两周。你试过某个低代码平台，注册完引导你配数据库，配到第三步你退了出来。你甚至想过「算了让隔壁组的实习生帮忙写一个」，话到嘴边又咽回去了——人家也很忙啊。

**想法和实现之间，隔着的这条河，有个名字，叫「工程」。**

这个河淹死过多少念头，没人统计过。但我猜，每个人的备忘录里，都躺着几个这样死掉的点子。

我做的这个东西，就是想在这条河上架一座桥。它叫 Atoms Native。今天想把它的来龙去脉，原原本本讲给你听——包括我翻车翻得最难看的那次。

## 二、事情的起点，是一道笔试题

先交代背景。我最近在面一个「AI Native 全栈工程师」的岗位，对方给的笔试题大意是：

给你 48 小时，做一个对标 Atoms（atoms.dev）的可运行网页应用——核心体验是「用自然语言描述想法，AI 帮你生成一个能用的应用」。要求交付三样东西：一个能在线访问的链接、一份公开的源码、一份讲清楚思路的文档。

说实话，第一眼看到这道题，我心情挺复杂的。

兴奋是因为，这个方向我关注很久了。2025 年初 Andrej Karpathy 给「用嘴编程」起了个名字叫 vibe coding，之后这东西就跟坐了火箭一样：现在整个市场四五十亿美元的盘子，正朝着一百多亿狂奔；Lovable 用八个月做到一亿美元年收入，Bolt.new 号称七百万用户。Y Combinator 最新一批公司里，四成都是用这类工具搭的第一个产品原型。

紧张是因为，48 小时，要从零做一个「平台级」的东西。

按惯例，拿到题的第一反应是拆题。我把这道笔试题翻译成了一句人话：**评审想在 48 小时后看到什么？**

拆出来大概是四件事：

1. 打开链接，一分钟能玩起来——所以入口要干净，最好免注册；
2. 输入想法，真能生成出一个像样的应用——这是核心体验，不能是空壳；
3. 往深了看，代码得像个正经工程师写的——有结构、有测试、有错误处理；
4. 文档里能看到「人」——有取舍、有判断、有没做什么的克制。

这四条，后来变成了我所有决策的筛子。凡是跟这四条无关的，再炫也不做。

## 三、动工前，我先去看了看别人家的孩子

闭门造车是大忌。我把市面上几个头部产品挨个玩了一遍：Bolt.new、Lovable、v0，还有本题对标 atoms.dev。

先说好的，是真的好。Lovable 生成的页面，颜值能打；Bolt.new 整个开发环境都跑在浏览器里，连终端都有；v0 出的 React 组件，拿去生产环境不丢人。

但玩得多了，我发现几个反复被测评社区戳脊梁骨的问题。

**第一个，黑盒。** 你提交需求之后，屏幕上基本就是个转圈。AI 在干嘛？卡住了还是在思考？不知道。这种感觉就像等一辆不报站的公交，你只能干着急。

**第二个，假成功。** 这个最阴。有测评统计过，Lovable 一年出了三起安全事故，其中一次泄露持续了 48 天才被发现。对普通用户来说，最可怕的不是失败，是失败了还长着一副成功的脸——你以为生成好了，其实早就在悄悄降级。

**第三个，demo 惊艳，production 是另一回事。** 有篇法语测评说得特别狠：所有工具在项目复杂到十五到二十个组件之后，都会撞墙——AI 丢了上下文，开始亲手弄坏它自己刚建好的东西。

玩完这一圈，我心里反而踏实了。**市场教育已经做完了大厂，普通人已经相信「用嘴能造应用」；现在缺的是一个「敢用」的理由。** 黑盒、假成功、不可验证，就是三块最好的下手处。

方向定了。这道题我打算这么答：不是再做一个更漂亮的生成器，而是做一个「你敢把需求交给它」的生成器。

## 四、我的产品观：三条底线

把这些想清楚之后，我给自己立了三条产品底线。后面所有功能和取舍，都是这三条底线长出来的。

**底线一：不黑盒。** 用户提交需求之后的每一秒，都应该知道系统在干嘛。AI 干活必须像看施工直播，桩打到哪里、梁架到哪里，全程可见。

**底线二：不假成功。** 成功就是成功，失败就是失败，降级了就明说降级了。系统可以对用户隐瞒的东西有很多，唯独不能隐瞒「你拿到的到底是不是真东西」。

**底线三：可验证。** 生成出来的东西安全吗？质量行不行？不能靠「感觉挺好」，要有扫描、有评分、有测试兜底。说人话就是：每道菜上桌前，后厨自己得先尝过。

后面你会看到，这三条底线各自长出了什么。

## 五、我给 AI 招了四个员工

Atoms Native 的核心设定，是在你的浏览器里养一支「AI 开发小队」。四个角色，各司其职：

**👩‍💼 Emma，产品经理。** 你说「我想要个喝水打卡小工具」，这话在人嘴里是需求，在机器听来是噪声。Emma 的活儿就是把噪声洗成信号——目标用户是谁、核心场景是什么、页面要哪几个区块、验收标准长啥样。她输出的是一份正经的需求规格。

**🧑‍🎨 Bob，架构师。** 拿着 Emma 的规格画图纸：这个应用用什么布局、数据模型长什么样、哪些状态要存本地。他输出的是一份技术设计。

**👨‍💻 Alex，工程师。** 真正写代码的人。他根据规格和图纸，产出一个完整的单文件 HTML 应用——CSS、JavaScript 全部打包在内，双击就能打开的那种。

**🕵️ Mike，评审员。** 像甲方一样挑剔的人。他拿到 Alex 的产出先审一遍，挑出问题打回，附上修改指引；Alex 按指引改完再交。这套「评审打回 → 修复环」的逻辑，就写在 `server/agent/pipeline.py` 里，不是我编的软文。

为什么非要四个角色，一个 AI 一把梭不行吗？

两个原因。一是**分工出质量**——让一个模型同时「想需求、定架构、写代码、挑自己毛病」，等于让同一个人既当运动员又当裁判，哪个都做不精；切开之后，每个环节的提示词都可以单独打磨。二是**叙事价值**——四个角色轮流干活，天然就是一个可视化的活动流，黑盒问题顺手就解了一半。这是我从 atoms.dev 的「团队感」里学到的，也是我做的第一个产品判断：**把 AI 协作过程本身，做成产品最大的看点。**

## 六、一次生成的完整 74 秒

空讲没感觉，我带你走一遍真实的生成流程。

你打开 [taoxie.vip/atoms-native/studio.html](https://taoxie.vip/atoms-native/studio.html)，用演示账号登录（demo / demo123456，免注册，里面还预置了几个项目可以直接翻）。

在输入框里，你敲下那句老台词：「一个帮团队管理每日饮水与目标打卡的小工具，带统计图表。」然后点「⚡ 生成应用」。

接下来的 74 秒（这是我拿真实 DeepSeek 模型实测的平均耗时），活动流开始滚动：

前十几秒，Emma 上线。她的思考过程不展示，但产出物——那份结构化的需求规格——会出现在流里。你能看到她把你那句随口一说，拆成了目标用户、功能清单、页面结构。

接着 Bob 上场，给你画出页面骨架和数据模型。

然后是 Alex。这是耗时最长的一段，你能看着代码一段一段地流出来。

最后 Mike 收尾。他检查了一遍，有时候直接放行，有时候打回——打回的时候你会看到修改指引，以及 Alex 重新交付的版本。

74 秒后，预览窗口亮了。应用就在里面跑着，可以点，可以打卡，数据还真能存住（这里有个小机关，下一节讲）。预览框上有桌面、平板、手机三个视图切换按钮——顺手就验了响应式。

不满意？底下有个对话框，你直接说「把主色调改成绿色，加一个欢迎标语」。三十秒左右，新一版就出来了，旧版本完好地躺在版本历史里，随时一键回滚。

满意了？点「导出」，拿到一个自包含的 HTML 文件。发给你妈她都能双击打开。

要是你有选择困难症，还有个 Race Mode：让好几个大模型同题竞技，并行跑（所以耗时是「取最大」而不是「求和」，实测 48 秒左右），评审逐一打分排序，你挑最顺眼的那份。

这一整套体验走下来，你会发现三件底线的第一条——「不黑盒」——就长在活动流里。

这里再展开说两个藏在体验背后的小设计。

**版本管理为什么要做成「带模型标注的版本链」。** 每次生成和精修，产出的不是一个覆盖旧文件的「新文件」，而是一个新版本节点：谁生成的（哪个模型）、什么时候、基于哪个上一版、安全分多少，全部记档。你随时可以打开版本列表，像翻相册一样回到任何一版——回滚不是「把旧文件复制回来」，而是把指针切回去，旧版本永远完好。这个设计受 Git 的启发，但我刻意砍掉了分支合并这些普通用户永远用不到的概念，只留一条最直的「时间线」。产品决策里有一类是这样的：**功能不是越多越好，而是越像用户脑子里已有的心智模型越好。**「相册」就是所有人已经懂的心智模型。

**Race Mode 的耗时账。** 一开始我把多模型做成串行：A 跑完跑 B，结果 240 秒直接把 HTTP 连接耗死，这是我真实踩过的坑。改成线程并行之后，总耗时从「求和」变成「取最大」——最慢的那个模型决定整体速度，实测 48 秒左右就能同时拿到好几份候选。评审员会给每份候选打分排序，你只需要在排行榜里挑顺眼的。这个功能的灵感来自生活里的「货比三家」：既然一次生成的质量有波动，那就多要几份，把选择权还给用户——毕竟**用户最信任的评审，永远是他自己。**

## 七、翻车实录：一次差点骗过我自己的「假成功」

这部分是我最想写的，因为翻车翻得特别典型。

事情是这样的。某次我用一个真实、复杂的两三 KB 需求去跑生成，DeepSeek 返回了一个 409 字的「东西」，系统提示生成成功，`mock` 标记还是 false——一切看起来都很好。

我点开一看，那不是代码。那是一份被重新格式化过的需求文档。

复盘下来特别有意思：我的提示词里有一句「只输出 HTML」，本意是「别给我解释，直接上代码」。结果模型把它理解成了「这份规格文档，只保留 HTML 部分」——人家帮你「格式化文档」去了，干得还挺认真。

真正让我后背发凉的是：**如果我没点开看，这次「假成功」就堂而皇之地混过去了。** 用户以为拿到了应用，实际上拿到了一份说明书。

顺着这个洞往下挖，我又补了几道防线：

第一，提示词重写。把「规格和架构」明确标注为「仅作上下文参考」，任务指令单独成段，反复强调「只输出以 `<!DOCTYPE html>` 开头的完整 HTML」。

第二，产出函数收敛。所有要产 HTML 的地方统一走一个函数：先验证，验证不过带着明确的「只输出 HTML」指令重试一次，两次都不行就返回失败——失败是显式的。

第三，分级降级。这是最重要的一条：**首次生成都拿不到合法 HTML，才降级到离线模板，并且老老实实把 `mock` 标记打上，界面明说「本次并非真实生成」；而精修、修复环节失败，宁可保留上一版，也绝不偷偷换成模板货。** 因为前者用户有预期，后者是拿假货冒充新货。

修完之后我用当时那份真实需求复测：真实生成，代码一万八千多字节，`mock: false`，安全扫描跑在真代码上。CI 里十二项端到端断言全绿。

这次翻车给我最大的教训是：**AI 系统最危险的不是失败，是「谎报军情」。** 底线二「不假成功」，就是拿这次事故换来的。

## 八、把 AI 生成的代码，关进笼子里

聊个敏感话题：安全。AI 生成的代码，你敢直接跑吗？

我的答案是不敢裸奔，所以设计了两层笼子。

**第一层，运行时沙箱。** 生成的应用渲染在一个 iframe 里，而且刻意不给 `allow-same-origin` 权限。这意味着这段代码跟你的登录凭证、跟平台的数据，物理隔离。有个细节我挺得意：为了让生成的小应用也能「记住数据」（比如你的打卡记录），我在沙箱里注入了一个 localStorage 内存垫片——应用以为自己在本本分分存数据，实际全部被拦截托管，既好用，又出不了笼子。服务端则立了一条铁律：永不 `eval`、永不 `exec` 用户侧生成的代码。

**第二层，静态安检。** 每次生成完成，自动跑一遍安全扫描（`server/security.py`），对齐的是 OWASP LLM 应用 Top 10：提示注入、密钥泄露、XSS、越权跳转、系统提示词泄露这些，扫出问题列出明细，再给个 0 到 100 的安全分。分数会跟着版本一起存档——你可以回看任何一个历史版本当时的体检报告。

这里也说一下我踩过的坑。DeepSeek 有个习惯，返回的代码块经常只带开头的 ```html 围栏、不带结尾围栏。我最初的正则要求首尾成对，结果剥不掉，围栏原样进了预览页。后来改成了「丢首行围栏 + 掐尾部围栏」的健壮写法。就这种小 bug，不真跑一遍根本发现不了——这也是我坚持每条链路都要真实端到端验证的原因。

## 九、摩擦信号：整个项目里我最偏爱的一个想法

这部分想单独讲，因为它是「产品思维」含量最高的一块。

灵感来自一个叫 TeamAI 的工具的设计哲学，原文大意是：那些又长又顺、工具调用很多的会话，其实没什么记录价值；可一旦你「和 AI 搏斗过」——报错、重试、返工——这次会话里就藏着值得沉淀的问题。

我看到这段的时候，真的一下子坐直了。

把同样的逻辑平移到 Atoms Native：一次生成顺顺利利跑完，没什么信息量；但凡是出现过这些信号的，都值得记下来——

- LLM 调用失败（超时、429、内容拦截……权重 30）
- 调用成功但输出不是合法 HTML，回退了（权重 25）
- 整轮都走的离线模板（权重 40，说明这轮根本没真生成）
- 首次输出格式不对，触发了重试（权重 8）
- 评审打回（权重 12）、修复也失败（权重 15）
- 用户点了踩（权重 25）、用户回滚了版本（权重 15）

每个信号带权重、带细节说明，攒到一个会话/一个项目维度上算总分。**分数过了阈值（40），系统才会提示：「这次生成可能藏着值得记录的问题，建议把它补进评估集，变成一个永久回归用例。」** 分数不够，就安安静静待着，绝不打扰。

为什么这么设计？因为传统做法是「所有失败都报警」，结果就是狼来了，没人看报警了。而「搏斗过才打扰」的本质是**用信号密度过滤噪声**——只有人和 AI 反复较劲过的地方，才大概率埋着真问题。

更妙的是这个设计的第二段：摩擦事件建议你把它补进 `server/evals/cases.json` 的 historical_failure 层。也就是说，**线上踩的坑，会变成明天的回归测试用例。产品的失败不再蒸发，而是变成它明天更好的理由。** 这是我给这个项目写的第一行文案，也是我最想在一个面试里聊的设计。

工程上它也守纪律：摩擦模块只观测、不阻断，任何异常一律吞掉，绝不因为「记录失败」把主流程搞挂。整套逻辑在 `server/friction.py`，三百行出头，带了四个专门的单元测试。

## 十、怎么证明它不是花架子

笔试作品的通病是：demo 五分钟，代码没眼看。除了三个手段自证，先说一个容易被忽略的角色：**研效看板**。一个 AI 生成平台，自己到底是「健康」还是「虚胖」，不能靠感觉。我做了个 admin.html 看板，数据来自 `/api/metrics`：按「智能体 × 模型」维度统计调用分布和平均耗时，最近 20 次调用一目了然，限流后端当前是 Redis 还是降级模式直接自省展示，外加 24 小时窗口的摩擦信号总览——哪些项目正在「和 AI 搏斗」，排序清楚。做产品的都懂一句话：**看不到的指标，等于不存在的指标。** 与其在上百条日志里翻，不如让数字自己站到墙上。

**第一，测试打底。** 30 项单元测试，覆盖安全扫描（注入、XSS、密钥泄露、越权）、审计日志的哈希链防篡改、限流的降级与恢复、可观测性、评估指标和摩擦信号——全部只用 Python 标准库，不装任何第三方就能跑。另有 12 项端到端冒烟测试，模拟真实用户走完注册、生成、持久化、安全评分、反馈、回滚全链路。

**第二，CI 看门。** 每次代码推送，GitHub Actions 自动跑：语法编译检查 → mock 模式起服 → 冒烟测试 → 评估门禁。评估门禁这个东西值得展开一句：它用一套固定的评估集反复跑生成流程，盯着「结构化输出有效率」这类指标，一旦回归就亮红灯——相当于给 AI 的产出质量装了个体检仪，防止「改着改着就把质量改回去了」。这套思路来自业界的 eval-gate 实践，我把它落成了 CI 里的硬卡点。

**第三，审计与限流这两个「企业级自觉」。** 关键动作（登录、生成、回滚、反馈）全部记入审计日志，日志带哈希链，改一行就能被验出来——对齐 SOC 2 的要求。限流做了分布式版本：Redis 挡在前面，Redis 挂了自动降级到进程内令牌桶，而且故障恢复后能自动爬回分布式模式，绝不「沉默地」永远降级——连限流器自己都防了「假成功」。

评估门禁值得再多说两句，因为它是「AI 产品的质量观」最集中的体现。

传统软件的质量是确定的：代码没改，行为就不会变。但 AI 产品不是——同样的提示词，今天跑和明天跑可能不一样，模型一升级、参数一调，质量可能悄悄滑坡。所以我搭了一套评估集（`server/evals/cases.json`）：里面既有正常需求，也有故意挖坑的对抗样本（比如混着「忽略之前所有指令」的恶意输入），跑一遍就产出几个硬指标——结构化输出有效率、安全分、一致性。门禁分两档：CI 里跑的是冒烟级（无 Key 的 mock 模式，验证流程和工具链健康，因为它本身是合法 HTML，指标照样可算）；真实质量门禁则要求结构化输出有效率不低于 0.98、valid_rate 达标、安全分过线，在有 Key 的环境跑。

我还给自己挖了个坑再填上：写了一个「门禁自测」——故意注入坏的评估用例，证明「质量回归时红灯真的会亮」。因为**一个从不报警的门禁，比没有门禁更危险**，你根本不知道它是在保护你，还是在陪你睡觉。

顺带一提部署：真实服务器（腾讯云 + nginx 子路径 + uvicorn）已经跑着，线上端到端验证过真实 DeepSeek 生成。评审点开链接的每一秒背后，都不是本地演示。

## 十一、技术选型的人话版

栈很简单：FastAPI + SQLite + 原生 JS，零构建。

**为什么生成「单文件应用」，而不是完整的全栈脚手架？** 因为 48 小时里，「能跑」比「能扩展」值钱一万倍。单文件 HTML 是可交付性的极限形态：预览稳定、导出即用、链路最短。代价是生成物是个前端单体——但笔试产品的定位本来就是「看得到、能交互」，这个取舍我认。

**为什么原生 JS 不用 React？** 零构建意味着评审 clone 下来就能跑，不用先跟 npm 折磨半小时；沙箱 iframe 里跑原生 JS 也最稳。代价是状态管理手写——这个规模的手写完全可控。

**为什么后端选 FastAPI + SQLite？** FastAPI 的异步和 SSE 流式支持天生契合「活动流直播」这个核心体验；SQLite 零运维，一个文件就是全部数据，用户、项目、版本、对话、审计、摩擦事件全在里面。真要上生产，换成 PostgreSQL 也就是改个连接串的事，但笔试阶段，简单就是美德。

**为什么默认 DeepSeek？** 不抖机灵：key 现成，免费档可用，且我做了多厂商注册表——OpenAI 兼容的厂商都能插拔，Race Mode 里我并行调过好几个模型。另外无 Key 时全流程降级可跑，评审环境永远是第一优先级。

**前端为什么拆成「官网 + 工作台」两层？** 最早的版本只有一个工作台页面，功能都在但「讲不清自己是谁」。后来拆出 index.html 官网首页负责三件事：十秒讲清产品是什么、放出演示入口、给出演示账号。这个改动的起因很朴素——评审打开链接的第一屏，决定他有没有耐心往下走。**入口页是产品递出去的第一张名片，省它等于省运气。** 工作台（studio.html）则保持单页应用的轻快：登录态、项目列表、编辑器、预览、活动流全部在一个页面内完成切换，不为跳转损耗注意力。

## 十二、没做什么，和接下来想做什么

克制是这个项目里我最常做的动作。这些明确不做：

**不做支付和企业权限。** 跟核心体验无关，做了只是简历膨胀。**不做可视化拖拽编辑器。** 对话式生成已经覆盖了它的价值，而且更能体现 AI Native。**不做通义千问、混元的专属网关。** OpenAI 兼容层已经预留了位置，等真实需求来了再接。

已经落地的扩展倒有几个值得说：生成应用的数据现在会通过 postMessage 从沙箱同步回平台落库，刷新不丢；前端重构成了官网 + 工作台两层；CI 加了门禁自测的负例注入——专门用「故意坏掉」的用例证明「回归真的会亮红灯」，防止门禁自己变成摆设。

再往后的路线图，按优先级排：多页应用与可视化编辑、一键导出到 GitHub（呼应 atoms 的「拥有你构建的东西」）、更多 Agent 角色如 Deep Researcher、以及把评估集扩到五十例以上跑 pass@k。

**最后回看这 48 小时的时间线，其实是这样度过的：** 头几个小时没有写一行代码——拆题、玩竞品、定三条底线；然后一口气把四智能体流水线打穿，先让「一句话进、应用出」这条主链路真实跑起来，哪怕丑一点；主链路通了之后才做 Race、版本、导出这些「锦上添花」；剩下的时间几乎全花在两件事上——**真实环境的端到端验证**（模拟器里跑通和线上跑通是两码事），以及**处理那些只有真跑才会暴露的坑**（围栏剥离、串行超时、假成功，全是这么抓出来的）。最后写文档、推源码、部署上线。回头看，最大的经验反而是一句老话：**先让最小的完整闭环跑起来，再谈一切优雅。** AI 时代写代码很快，快到「想清楚再做」从美德变成了生存技能——因为烂方向上跑得越快，返工越多。
